## 目标与范围

M6 只回答一个核心问题：在 E3 的 trajectory-level GRPO 主体、数据、SFT 起点、reward、mask、生成参数
和优化配置保持不变时，加入下面这个简单、可审计的 turn-level correction，是否改善学习效率、最终性能
或工具行为：

\[
A_{\mathrm{turn}}(t)=A_{\mathrm{traj}}+\beta\left(s_t-\bar{s}_t\right),\qquad \beta=0.5.
\]

- `A_traj` 必须由 veRL 0.8.0 与 E3 完全相同的 native GRPO 路径产生；
- `s_t ∈ {0,1}`，只有该 assistant turn 的工具调用成功执行、且结果被后续 assistant reasoning/final
  derivation 采纳时为 1；
- `s̄_t` 是同一 prompt/UID group 内、同一 assistant turn position 上已实际出现该 position 的 rollout
  的 `s_t` 算术均值；
- 该 assistant turn 的全部 policy-generated token 使用对应 `A_turn(t)`；
- tool/environment return token 和 padding 继续保持 E3 的 `response_mask=0`，不进入 policy loss；
- 本计划定义未来获批后的 Tier A执行；本次任务只制定计划。不得在看到结果后自动扩展 Tier B/GiGPO、
  调 `β`、换 adoption定义或追加 seed。

M5/E7 保持 intentional defer；本 Milestone 不创建、实现或运行 E7，也不修改或重跑 E3/E4/E6 历史结果，
不创建 M5 tag。

## veRL 0.8.0 / E3 真实数据流核查

### Rollout、turn 与 mask

1. `ToolAgentLoop._handle_generating_state()` 每次 assistant generation 把生成 token 追加到
   `response_ids`，并向 `response_mask` 追加同长度的 1；assistant tool-call JSON 本身也是 policy token，
   因而 mask=1。
2. `_handle_processing_tools_state()` 将 tool response 经 chat template 编码后追加到同一 response tensor，
   并向 `response_mask` 追加同长度的 0；当前配置 `max_parallel_calls=1`。
3. agent-loop postprocess 把 response 右侧 padding，并以 response attention mask 再乘一次，所以 tool return
   与 padding 都是 0；`response_ids`、`response_mask` shape 均为 `[batch, 3072]`。
4. 当前 rollout output 保留 `__num_turns__`、aggregate `tool_*_count`、空的 `turn_scores/tool_rewards` 等，
   但没有 per-assistant-turn token span、per-call execution status/result 或 adoption evidence。
5. E3 raw rollout JSONL 只含解码后的 input/output、score、reward components 与 `sample_id`；没有 UID、
   token IDs/mask、turn spans 或 advantage。历史 E3 raw 不能被无损地 retro-fit 成 token-level turn ledger。

因此 E5 必须在现有 repo-local agent-loop 扩展点生成结构化 per-turn metadata；turn boundary 以 rollout
过程中记录的 assistant token start/end 和原生 response mask 为准，不从最终纯文本重新用 XML/regex 猜边界。
regex 只允许用于 adoption 内容匹配和 Hermes parser error audit，不得用来决定 token span。

### Reward 与 trajectory advantage

1. E3 reward 由 `rl/custom/reward.py:compute_score` 产生，answer 1.0 + format 0.1，shaping 关闭；parser、
   execution 和四次调用后仍无 boxed answer 的 budget exhaustion 显式进入 metadata/metrics。纯 response
   length clipping 主要通过长度/缺失 boxed 暴露，legacy `truncated` 字段不保证覆盖它；E5 必须新增独立
   `termination_reason` audit，但不改变 E3 reward 或 legacy metric 口径。
2. `RayPPOTrainer.fit()` 在 reward 后把 `token_level_scores` 赋给 `token_level_rewards`，E3 不在 reward
   中加 KL；old/ref log prob 保持标准路径。
3. `ray_trainer.compute_advantage()` 对 GRPO 调
   `core_algos.compute_grpo_outcome_advantage()`：先对每条 response 的 token reward 求和得到 scalar score，
   按随机 UID 分组，用 torch sample std（`torch.std` 默认 correction=1）归一化，再将该 scalar
   `A_traj` 乘 `response_mask` 广播到全部 policy token。
4. actor policy loss 直接读取 `[B,L]` 的 `advantages` 和 bool `response_mask`；tool/padding token 即使
   advantage tensor 被意外写值，也不应进入 loss，但 E5 仍要求它们的 advantage 显式为 0，避免审计歧义。

### 原生扩展点的边界

veRL 有 custom advantage registry，但当前 `ray_trainer.compute_advantage()` 给普通自定义 estimator 只传
`token_level_rewards`、`response_mask`、`uid` 和 algorithm config；不会传包含 per-turn ledger 的完整
`DataProto`。只有 hard-coded `gdpo` 分支额外传 batch，冒充 GDPO 不符合 E5 定义。`fit()` 又直接调用模块级
`compute_advantage()`，没有 trainer method hook。

结论：**YAML-only 或只注册一个 custom estimator 不能忠实实现 Tier A。** 但本次不需要像 E7 一样复制
`TaskRunner.run()` 或约 409 行 `fit()`；可以把内部边界压缩为 E5 专用 Ray TaskRunner 中的两个临时、
fail-closed wrapper，具体见下节。即使不修改 site-packages，这仍触及 trainer 内部 advantage/data-flow，
实际实现前必须获得用户专项批准。

## Tier A 冻结语义

### 1. 一个 turn 的结构化记录

E5 中的 `t` 是从 0 开始的 **assistant turn position**，不是 tool call count，也不是 veRL 的 user+assistant
总 turn 数。每条 rollout 在 agent loop 结束时必须产生：

```text
rollout request/trajectory UID
response_length_unpadded
assistant_turns[]:
  turn_index
  policy_token_start                 # inclusive, response-relative
  policy_token_end                   # exclusive
  parsed_call_count
  executed_call_count
  parser_error_count
  execution_status
  visible_tool_response_text          # 实际注入并编码进 rollout 的 post-process/post-truncation text
  raw_sandbox_stdout                  # optional audit-only；禁止用于 adoption/s_t
  normalized evidence candidates      # 只从 visible_tool_response_text 派生
  later_assistant_turn_indices
  adoption_status / adoption_evidence
  s_t
trajectory_truncated / budget_exhausted
```

trainer 随机 `uid` 是 prompt group UID，会在 `n=8` rollout 间重复；它不等于 trajectory UID。E5 agent
loop 另保留原生 request ID，driver 再以 `(group_uid, request_id)` 形成唯一 trajectory key，严禁只用
`sample_id` 区分同 prompt 的八条 rollout。

结构化 span 必须覆盖 `response_mask==1` 的每一个未 padding token且恰好一次；tool-return run 必须全部
对应 `response_mask==0`。span overlap、gap、越界、非单调、ledger 长度与 response length 不一致，或
`max_parallel_calls=1` 却观察到多个 executed call，均为 alignment error，立即失败，不以 reshape/广播修补。

### 2. `execution_success` 的确定性定义

对 assistant turn `t`：

- Hermes 成功解析、dispatch 到唯一允许的 `code_interpreter`、参数严格是一个字符串 `code`、sandbox
  返回 `status == "ok"` 时，`execution_success=1`；stdout 为空而变成 `(no output)` 仍是 execution
  success，但通常没有可采纳 evidence。
- malformed/incomplete tool-call、JSON/参数 schema 错误、unknown tool、helper/dispatch exception、
  sandbox `error`、`timeout`、signal/resource failure 都是 `execution_success=0`，并保留细分 status。
- 无 tool call 的 assistant turn：`execution_success=0`、`adoption_status=no_tool`、`s_t=0`。
- 当前 `max_parallel_calls=1`。如果一个 turn 解析出多个 call 但只执行第一个，记录
  `multiple_parsed_calls`，训练映射保守为 `s_t=0`，并单独进入 audit；如果实际执行数大于 1，则是配置/
  对齐违约，阻断 batch。这样不会静默挑一个有利 call 记 1。
- parser error 与一个成功 call 同时出现时，仍保守记 `s_t=0`，并保存 success/error 双重事实；不让部分
  可解析 payload 掩盖同 turn 的 malformed call。

### 3. `adopted` heuristic v1

`adopted` 不是因果语义 judge，而是可复现的高精度文本 evidence heuristic。它只在
`execution_success=1` 后运行，并冻结为 `toolcredit_adoption_v1`：

1. **搜索范围**：只搜索该 tool result 之后的 assistant policy spans `j>t`，包括后续 reasoning、后续
   tool-call code 和 final answer；排除当前 call payload、所有 tool/environment spans、system/user prompt。
2. **结果候选**：唯一输入是 pin veRL `_call_tool()` 已完成 post-processing 和配置截断后返回、随后作为
   tool message 实际送入 chat template并编码进 rollout tool span 的 `ToolResponse.text`，记为
   `visible_tool_response_text`。先验证该字符串与对应 encoded tool span属于同一次 call，再从中移除
   ANSI/control、做 Unicode NFKC并折叠 whitespace。sandbox原始 stdout/未截断 response可另存为
   `raw_sandbox_stdout` 供审计，但**绝不能**生成 candidate、adoption evidence或影响 `s_t`；仅存在于 raw
   text、却因 post-processing/truncation未对模型可见的值一律不得匹配。`(no output)`、error/status文本没有
   candidate。超过 32个 numeric candidate或无法稳定解析的巨大/混合可见输出标记 `ambiguous_output`，
   不挑选有利子集。
3. **数值匹配**：支持带符号整数、小数、逗号分组、科学计数法、负数和 `a/b` 分数；用
   `Decimal/Fraction` 标准化。分数/整数做精确有理数匹配；小数/科学计数法允许固定容差
   `abs(x-y) <= max(1e-9, 1e-6*max(abs(x),abs(y)))`。later text 中的 `\frac{a}{b}` 与 `a/b` 视为同值。
   非有限值不参与；0/1 等短值仍必须满足下述 integration evidence，不能仅因偶然出现而记 adopted。
4. **字符串匹配**：对长度 4–80 的非纯数值 output line 和不超过 80 字符的完整 scalar output，做
   NFKC、casefold、whitespace-collapse 后的 token-boundary exact substring；常见 status/noise word 不作为
   独立 candidate。更长文本不做模糊 substring 采纳。
5. **integration evidence**：candidate 必须满足至少一项：
   - 与 final `\boxed{}` 内容数值等价/字符串一致；
   - 在同一 clause/window 中参与等式、变量赋值、算术/比较表达式；
   - 与冻结的推理 cue 同窗出现（如 `therefore/thus/hence/so/we get/gives/using/substitute/result/answer`）；
   - 作为数值 literal 出现在后续已结构化解析的 `code_interpreter` code AST 的计算节点中，而不是注释或
     string literal。
6. **仅引用不算采纳**：若值只出现在 `the tool returned/output/says ...` 一类报告/引用窗口，且没有
   boxed、运算、赋值或上述 integration cue，则 `adoption_status=mentioned_only`、`s_t=0`。值出现但没有
   integration evidence 也同样为 0。
7. **状态映射**：`adopted` 才映射为 1；`not_found`、`mentioned_only`、`ambiguous_output`、
   `ambiguous_multiple_calls`、`no_output`、`no_tool` 均映射为 0。每个状态仍单独保存，不能在统计中把
   ambiguous 静默并入普通 not-adopted。
8. **trajectory 截断**：如果 trajectory截断前已经出现满足规则的 later evidence，可记 1；否则记
   `unobservable_truncated` 并训练映射为 0，不能声称“确定未采纳”。trajectory-level truncation/reward
   仍完全沿用 E3。这不同于上游 tool-response字符串截断：后者在 candidate提取前已经完成，被移除的 raw
   内容对模型不可见，即使 audit中保留也永远不能支持 adopted。

这一规则有不可消除的噪声：文本共现不等于真正参与了 hidden reasoning，保守规则也会漏掉释义使用。
因此结论必须写成“heuristic adoption evidence”，不能写成真实 step value/PRM；不引入模型型 PRM、judge
或额外 API。

### 4. heuristic noise audit

正式 run 前的 smoke 轨迹中，按自动状态分层、再以 `(sample_id, turn_index)` 的稳定 hash 排序抽取最多
50 个成功 tool turns；尽量平衡 `adopted/not_found/mentioned_only/ambiguous/truncated`，不足则报告实际数。
人工标签在不看 reward、`A_traj`、`A_turn` 和 final correctness 的情况下判
`adopted / not_adopted / uncertain`，保存原 result、later span、match evidence 和理由。

必须报告：各自动状态分母、人工 uncertain rate、对确定人工标签的 precision/recall/F1 和 Wilson 95% CI。
80% precision自动门槛的分母，是自动标为 `adopted` 且人工给出确定 `adopted/not_adopted` 标签的 cases；
`uncertain` 不计入该分母。只有该分母至少为 10时才自动应用门槛：precision <80% 阻断 formal run并请求
用户决定是否 version bump，precision ≥80% 才通过这一自动门槛。若分母少于 10，必须人工审计全部可用的
auto-adopted cases并提交分母、labels和 CI供显式 review；不能自动视为通过，也不能仅因小样本 point estimate
高于 80% 而放行。任何 token alignment error仍直接阻断。保守 heuristic的 recall不设事后调参门槛，只
如实报告。规则修改必须变成 v2，重跑所有相关 fixture、smoke与 audit，不能沿用 v1输出。

### 5. turn mapping 与 variable length group baseline

- 每个 assistant turn 的所有 policy token（包括 reasoning 和该 turn 的 tool-call JSON）使用同一
  `A_turn(t)`；该 call 后的 tool response token始终为 0 advantage/mask=0。
- final assistant turn 也接受 turn correction，因为 PLAN §10.1 明确要求“该轮所有生成 token”使用
  `A_turn(t)`，而 final 是 policy-generated assistant turn。它通常无 tool call，因此 `s_t=0`；这可能把
  同 position 的 final-answer turn 与另一 rollout 的 tool-call turn比较，是 position-aligned Tier A 的
  已知局限，不在计划阶段改成状态锚定或豁免 final。
- 同一 UID group 内按 assistant index 对齐。`s̄_t` 分母只包含实际存在 assistant turn `t` 的 rollout；
  缺失该 position 的短 rollout不进入分子也不进入分母。存在但无 tool call/final 的 turn 以 `s_t=0`
  正常进入。
- 某 position 只有一个 rollout 时 `s̄_t=s_t`，correction=0；不人为借用前后 position。
- group 必须恰有 `rollout.n=8` 条且 UID/sample 对齐；DP balance 可能重排 batch，但均值只能按 UID 聚合，
  不能依赖 row 邻接。

## Advantage integration 的 exact boundary

### 推荐的 repo-local 最小实现

仅在用户专项批准后，预计新增/修改边界为：

1. `rl/custom/turn_advantage.py`
   - 纯函数：span/ledger validation、candidate normalization/matching、`s_t` 生成、按 UID/position 计算
     `s̄_t`、token-level correction、audit row 构建；
   - `compute_turn_credit_data(base_compute_advantage, data, ...)` 先原样调用 pin 的 native
     `ray_trainer.compute_advantage()` 得到 E3 `A_traj`，再只改 `advantages/returns`；
   - debug 模式打印并断言 `response_ids/response_mask/turn_ids/A_traj/s_t/A_turn` shape，不做隐式 reshape。
2. `rl/custom/turn_credit_agent_loop.py` 与独立 agent-loop config
   - 继承现有 `ToolCreditAgentLoop`，不复制状态机和 sandbox；
   - 只记录 per-assistant span、per-call parser/dispatch/execution、实际编码的 post-truncation
     `visible_tool_response_text` 和 v1 adoption evidence；可选 raw stdout只进 audit-only字段，不能进入
     candidate/adoption/`s_t` data-flow；
   - 输出 response IDs/mask、reward 与状态转移保持原生/E3 行为。
3. `rl/launch/e5_turn_credit.py`
   - 复用 E3 的 config compose、路径解析、preflight、resume 与 run-dir protection；
   - 定义 E5 专用 `TurnCreditTaskRunner(TaskRunner)`。其 `run()` 在 Ray driver 内校验上述 veRL source SHA
     和原函数 identity，然后在 `try/finally` 生命周期中临时：
     1. 包裹 `verl.trainer.ppo.ray_trainer.compute_advantage`；
     2. 包裹 `RayPPOTrainer._log_rollout_data`，把 wrapper 已放进 batch 的 nested per-turn audit 持久化到
        对应 step raw JSONL；
     3. 调 `super().run(config)`，结束或异常时恢复原函数。
   - 用 `ray.remote(num_cpus=1)(TurnCreditTaskRunner)` 包装 subclass，再传给
     `main_ppo.run_ppo(config, task_runner_class=...)` 官方 TaskRunner 注入点；不复制 `TaskRunner.run()`，
     不 subclass/copy `fit()`，不修改 site-packages。
4. `rl/configs/e5_turn_credit.yaml`：保持 `algorithm.adv_estimator=grpo`，新增显式
   `turn_credit.enabled=true, beta=0.5, heuristic_version=toolcredit_adoption_v1` 和 E5 agent-loop 选择。
5. `rl/custom/test_turn_advantage.py`、E5 config/launcher tests、`rl/analyze_e5.py`、M6 run/watcher 脚本；
   同步更新 `rl/custom/CHANGES.md`。diagnostic freeze bundle 见后文。

wrapper 的顺序必须是：native GRPO → assert 得到的每条 trajectory policy-token advantage 为单一 scalar
`A_traj` → 按 UID/position 算 correction → 写回同 shape `advantages` 与 `returns` → actor update。old/ref
log prob、KL、PPO clip、loss aggregation、checkpoint、validation 全部原样复用。

### 为什么不使用其他边界

- 不把 turn signal 塞进 reward tensor：那会改变 `A_traj` 和 reward 语义，不再是指定公式。
- 不冒充 `gdpo` 或借用其他 estimator 名称：会混淆 estimator 和 config，且无法证明 E3 主体不变。
- 不通过 response mask 权重模拟 correction：actor 将 mask 转 bool，只能控制参与/不参与，不能表达
  `A_turn`。
- 不在 raw output 上离线 regex 生成训练 turn IDs：历史文本无法无损恢复 token span。
- 不复制 `fit()`：pin 源码已经提供足够小的 module-function interception point；复制大段 trainer 会扩大
  checkpoint/resume、sleep/wake 和 validation 风险。

### 专项 approval gate

上述两个 runtime wrapper 虽然 repo-local、可恢复且不修改 site-packages，仍改变 E5 的 trainer 内部
advantage/data-flow 和 logging。**实际创建这些文件前必须由用户明确批准 exact boundary。** 若实现核查
发现 module wrapper 在 Ray driver 中不能可靠生效，必须停下并展示新的边界；不得静默升级为复制 `fit()`。
任何需要复制 `TaskRunner.run()`、`fit()` 或直接 patch site-packages 的方案都需要新的专项批准。

E3 config/launcher 不导入 E5 TaskRunner、不注册 wrapper、不切 agent loop；E3 永远继续走当前原生路径。

## Controlled fixtures 与测试门禁

本节只定义未来测试；本次不运行。

### Fixture A — 交叉好/坏 turn，手算 expected

一个 UID group 有两条 rollout，trajectory reward 分别为 1 和 0。native veRL GRPO 使用 sample std：

```text
mean = 0.5
std  = sqrt(0.5) = 0.70710678
A_traj(rollout1) =  (1 - 0.5) / (0.70710678 + 1e-6) ≈ +0.70710578
A_traj(rollout2) =  (0 - 0.5) / (0.70710678 + 1e-6) ≈ -0.70710578

rollout1: turn0 good (s=1), turn1 bad  (s=0)
rollout2: turn0 bad  (s=0), turn1 good (s=1)
s_bar_0 = s_bar_1 = 0.5
beta * (s-s_bar) = +0.25 for good, -0.25 for bad

rollout1 A_turn = [+0.95710578, +0.45710578]
rollout2 A_turn = [-0.95710578, -0.45710578]
```

测试必须把每个 expected scalar映射到人为指定的多 token assistant spans，并证明 tool spans/padding 为 0。

### Fixture B — E3/disabled identity

- `turn_credit.enabled=false` 时 wrapper 输出的 `advantages/returns` 与 native GRPO逐元素、dtype、device、
  shape 完全一致，即 `A_turn(t)==A_traj`；
- E3 launcher 不安装 wrapper，函数 identity 与 source hash保持原样；
- reward、mask、old/ref log prob输入不变。该 fixture 是“E3 behavior 不变”的必要而非可选测试。

### Fixture C — 2/3/4 个 assistant turn

三条 rollout 的 `s_t` 固定为：

```text
R2: [1, 0]
R3: [0, 1, 1]
R4: [1, 1, 0, 1]

s_bar_0 = 2/3   denominator=3
s_bar_1 = 2/3   denominator=3
s_bar_2 = 1/2   denominator=2
s_bar_3 = 1     denominator=1, correction=0
```

验证缺失 position 不进入分母、存在的 no-tool/final `s=0` 会进入、每个 trajectory mask/span 对齐。

### Fixture D — execution success 但未采纳

成功 result 在 later assistant spans 中没有 integration evidence，或只有引用：

```text
execution_success=1
adoption_status=not_found/mentioned_only
adopted=0
s_t=0
```

数值、字符串、近似数值、科学计数法、负数、分数和 boxed match各有 positive/negative boundary test。
另做 visible-only negative test：一个值只存在于 `raw_sandbox_stdout`、但不在实际编码的
`visible_tool_response_text` 中，即使 later assistant使用该值也必须是 `not_found/s_t=0`；相反方向验证
candidate确实来自与该 call对应的 encoded visible text。

### Fixture E — failure、truncation 与 no-tool

覆盖 malformed Hermes JSON、schema/dispatch failure、sandbox error、timeout、成功无 stdout、解析多个 call、
截断前已采纳、截断导致不可观察、预算耗尽、第一 turn 即 final/no-tool。所有 error reason 必须保留，
ambiguous/unknown 映射 0 但不得丢失状态。

另锁定 pin veRL tool-response截断 fixture：当 Python `len(text)>512` 且 `truncate_side=middle` 时，tokenization
前的可见文本必须逐字符等于 `text[:256] + "...(truncated)..." + text[-256:]`。落在被删除中段的 candidate
不得影响 adoption/`s_t`；位于保留 prefix/suffix且满足其余规则的 candidate按正常 heuristic处理。

### Shape / UID / conservation assertions

每个 fixture 和 smoke 都必须逐项断言：

```text
responses.shape == response_mask.shape == turn_ids.shape
advantages.shape == returns.shape == responses.shape
len(uid) == len(per_turn_ledger) == batch_size
每个 UID 恰有 rollout.n 条
每个 response_mask==1 token 恰有一个 nonnegative turn_id
每个 tool/padding token turn_id==-1 且 A_turn==0
A_traj 在同一 trajectory 的全部 policy token 上为单一 scalar
s_t ∈ {0,1}; s_bar_t ∈ [0,1]
A_turn == A_traj + 0.5*(s_t-s_bar_t)
```

另做 batch reorder 测试证明按 UID 而非行邻接分组，以及不完整/重复 UID、NaN/Inf、metadata 长度错位均
fail closed。测试顺序是纯 CPU unit/fixture → 现有相关 core tests → resolved-config diff；通过前不得占 GPU。

- 源码实现、CPU fixtures、freeze review和人工 smoke/audit预计另需 **1–1.5个日历日**，不计入 GPU小时；
  等待独立批准的时间不计入执行时间盒。
- 若 E5稳定单步 wall-clock连续高于 E3基线 25%，先定位 adoption/logging I/O；不得用减少 batch、turns或
  response budget来隐藏额外成本。超过 14 GPU小时仍未完成时停止并请求用户决定。

### 磁盘预算与可复算门禁

依据 E3实测，一个完整 checkpoint约 21 GiB、两个保留点约 41 GiB、200-step decoded predictions约
432 MiB。E5预留如下：

| 项目 | canonical预估 | 写入/恢复峰值预留 |
|---|---:|---:|
| 两个完整 checkpoints | 42 GiB | 63 GiB（新 checkpoint完整落盘后再轮换） |
| train/val raw rollout + 全量 per-turn ledger | 2–5 GiB | 7 GiB |
| mechanism/heuristic/transition audit与索引 | 1–3 GiB | 5 GiB |
| config、metrics、TensorBoard、log、summary | 1–2 GiB | 3 GiB |
| 一次 recovery归档/半写缓冲 | canonical不计 | 25 GiB |
| **E5 formal合计** | **约 46–52 GiB** | **约 103 GiB峰值** |

- 每次 smoke/formal/resume 都现场计算 `remaining_peak_write`；最低可接受余量为
  `remaining_peak_write + 30 GiB safety margin`，不能只照抄本计划的历史 `df` 快照。
- 按上表，formal从零启动的当前参考下限约 **133 GiB**，执行时向上取整报告为 **135 GiB**；这是防止
  checkpoint轮换、恢复归档和 NFS写满的启动门禁，不是最终 run一定占用 135 GiB。若实际 retention或
  ledger估算变化，按公式重算并在 preflight记录。
- smoke参考峰值约 25 GiB，因此当前参考下限为 **55 GiB**；若保留 smoke checkpoint再启动 formal，
  该 checkpoint的实测占用必须另加到 formal `remaining_peak_write`，不能重复或漏算。
- 当前末次只读快照约 330 GiB，按参考门槛暂时充足，但不是未来授权；每次启动和恢复仍必须重查。

  只有用户明确批准时，才可精确删除该 smoke run的 `checkpoints/`。先记录目标绝对路径、实测大小、文件
  清单/hash与 tracker状态，删除后写 `checkpoint_cleanup.json`；不触及整个 smoke目录或其他 run。

  不得自行清理。

## Mechanism evidence 与预注册抽样

### 同一真实 rollout 的 E3 counterfactual vs E5 actual

历史 E3 raw 没有无损 token span/advantage；本计划不篡改历史产物，也不以文本 regex伪造 token audit。
E5 wrapper 对每条真实 E5 rollout同时保存：

- native GRPO刚产生、若走 E3 会广播到所有 policy turns 的 `A_traj`；
- E5 实际用于 actor update 的 `A_turn`；
- 两者在同一 response token layout上的映射。

这形成同一真实 trajectory 的算法内反事实：E3 rule 在全部 turn相同，E5只增加预注册 correction。E3正式
run确实走该 native rule由 E3 config、pin source hash 和 Fixture B证明；不需要重跑或 retro-fit E3训练。

### 至少 30 条 mixed-quality trajectory

eligible 定义在看 formal 结果前固定：至少两个 assistant turns，并在同一 trajectory内同时包含至少一个
`s_t=1` 与至少一个 `s_t=0` 的 tool-related turn；后者按 execution/parser error、success-but-unused、
mentioned-only、recovery、budget/truncation等细分。按类别配额后以
`sha256(run_name, step, uid, sample_id)` 排序选前项，不按 reward改善方向挑选。

目标至少 30 条，尽量覆盖：

- successful + adopted；
- successful but unused/mentioned only；
- parser/dispatch/sandbox/timeout error；
- error 后恢复与未恢复；
- budget exhaustion/truncation；
- no-tool/final turn与 variable turn count。

如果满足固定 eligible 定义的真实 trajectory不足 30 条，报告实际数、各类分母与证据不足；不得扩大定义、
混入 E4/E6或只挑有利案例凑数。

每条保存：

```text
run/step/sample_id/prompt UID/trajectory UID
turn index
native A_traj
execution_success + detailed status
adoption_status + matched candidate/evidence/offset
s_t
s_bar_t + position denominator
correction
A_turn
policy token span + response length
response_mask/tool span conservation
final score/reward/accuracy/format/invalid/truncated
```

审计必须定量证明：native E3 rule 对同 trajectory各 policy turn广播同一个 `A_traj`；E5 对问题 turn
降低相对 credit、对 useful turn提高或保留相对 credit。这里的“降低/提高”是相对同 trajectory native
baseline的 correction，不要求负 trajectory中的 useful turn必然获得正绝对 advantage。

## Performance、behavior 与 paired evidence

### Performance 主次指标

- fixed MATH500-100 greedy pass@1 曲线：step 0/25/.../200；
- early convergence：0–100 step trapezoidal normalized AUC为 primary，0–200 AUC和首次达到预注册 E3
  阈值（0.67/0.70/0.73/0.76）为辅助；
- final step-200 pass@1为主要终点，peak只作辅助，不能用 peak替代 final；
- 与 E3 同 step差值和 paired question exact counts；固定 100题中 1pt=1题，避免过度解释。

### 训练稳定性与工具行为

至少报告：response length、entropy、PPO KL、clip/pg loss、tool calls、per-call execution success/error、
parser error、invalid/format、truncation、错误恢复率、adoption/mentioned/ambiguous率、correction分布、各 turn
position 的 `s̄_t`/denominator，以及 mixed-quality trajectory比例。

错误恢复率沿用 PLAN：首次工具执行报错的 trajectory 中最终答案正确的比例；同时给 denominator，parser
failure与execution failure分开报告。E5新增行为指标不能反过来改 E3 reward或 fixed-panel pass@1口径。

### E3→E5 paired failure transition

按 M7 freeze执行并报告：

```text
total denominator
E3 failed -> E5 correct (fixed)
E3 correct -> E5 failed (new failures)
unchanged correct
unchanged failed
primary failure transition matrix
secondary tag transitions
exact count + paired bootstrap 95% CI
```

案例展示必须同时包含 fixed、regressed和unchanged，不允许只展示“E5修好的题”。某 failure类分母过小则
只报告观察值并标记 evidence insufficient，不宣称“已解决”。

## M7 interface

M6 向 M7只交付可复核接口，不在 M6提前执行全量 M7评测：

- freeze bundle及其 hash/批准 ledger；M7以该 bundle为唯一 panel、generation、tool、verifier、taxonomy、
  pairing和bootstrap输入；
- E5 step-200完整 checkpoint、resolved config/source/data/SFT/freeze manifest，以及 E3/E5 fixed-100全部
  trajectories、per-turn mechanism audit、paired transition和 denominator；
- raw base、SFT、E3、E5四阶段 checkpoint的稳定 role/路径清单。M7对四者运行 full MATH500、AIME24/25、
  GSM8K-200时必须使用同一冻结 evaluator，不能把 E3旧生成与 E5新协议生成混入同一四阶段主表；
- M6可复用 E3现有 fixed-100 validation做严格同 cadence E3→E5比较，但 M7四checkpoint正式诊断需要按
  freeze bundle统一生成并保存全部 trajectories。若 protocol任何部分 version bump，四个比较checkpoint
  全部重跑，不能只给 E5更新；
- M7产物至少能由 `(protocol_version, checkpoint_role, question_id, sample_index, seed)` 唯一定位，保持
  primary/secondary标签、人工裁决与原始 trajectory之间的双向 evidence pointer。

## Acceptance criteria

M6 只有同时满足以下条件才可验收：

1. exact runtime boundary得到专项批准；没有 fork/升级 veRL、直接改 site-packages或复制大型 `fit()`；
2. Fixture A–E、shape/UID/alignment、E3 identity和 config/behavioral diff tests通过，相关回归无退化；
3. 五文件 M7 freeze bundle在任何 E5 smoke/output前冻结，有精确 ID、闭包 hash、人工批准和
   zero-overlap证据；
4. 5-step smoke通过，人工核对真实 turn/adoption/advantage/token mapping；heuristic audit落盘且达到上述
   formal-run gate；
5. 独立从 SFT起点的 E5 `β=0.5` 完整 200-step run及五件套齐全；
6. 至少 30条固定定义的 mixed-quality trajectory机制审计，或如实报告实际不足数及原因；
7. fixed-panel performance/AUC/final/peak与稳定性、工具行为均按 E3平行口径报告；
8. E3→E5 paired transition包含完整 denominator、fixed/new/unchanged、taxonomy transition和bootstrap CI；
9. 正结果以 failure transition和mechanism evidence限定归因；无差异/负结果同样作为有效结论，讨论短
   horizon、position alignment、heuristic noise和固定 `β`局限，不追加事后调参run；
10. README、technical report、主结果/badcase证据索引、`LOG.md/HANDOFF.md`在用户授权的验收阶段同步。

state-anchored/GiGPO或多seed设置。
