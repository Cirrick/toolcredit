## 目标

M5 以已验收的 E3 为严格 baseline，完成三个互相平行、各自可归因的实验：

1. **E6 no-mask**：仅把 tool/environment return token 从 loss mask 中放开，构造可解释的工程反例。
2. **E4 reward shaping**：用两条必做 run 分别测量 execution bonus 的作用，以及在 execution bonus 上加入
   budget penalty 能否抑制过度调用/reward hacking 并保留收益。
3. **E7 DAPO-style dynamic filtering/sampling**：仅改变每次有效 actor update 的 prompt/group 选择方式，
   过滤组内标量 reward 零方差的 group 并动态补采样，回答它是否减少无有效 GRPO 梯度的 rollout 浪费。

三者原则上均从同一 SFT checkpoint 独立启动，不从 E3 step-200 续训。M5 不实现 M6 的 turn-level
credit，也不改变 verifier 的正确性口径。

### veRL 0.8.0 dynamic filtering 核查结论

当前环境实际为 veRL 0.8.0。其
`verl/trainer/config/algorithm.py:FilterGroupsConfig` 声明了三个字段：

```yaml
algorithm:
  filter_groups:
    enable: false
    metric: null
    max_num_gen_batches: 0
```

字段注释称其供 DAPO/Entropy 使用，`max_num_gen_batches <= 0` 表示不设上限。但对 pin 版本源码的
全量搜索表明：这些字段只在 config dataclass 中声明；
`verl/trainer/ppo/ray_trainer.py:RayPPOTrainer.fit()` **没有读取或执行** `filter_groups`，而
`verl/trainer/main_ppo.py:TaskRunner.run()` 直接构造标准 `RayPPOTrainer`。官方 v0.8.0 tag 的对应源码
结论相同。因此：

> **E7 不能通过当前 veRL 0.8.0 的现成 YAML 配置单独实现。** 仅设置上述字段会形成“配置看似开启、
> 实际没有过滤”的静默错误，验收时必须用行为测试防止这一点。

官方动态采样参考实现位于独立的 `verl-recipe/dapo/dapo_ray_trainer.py`，使用定制
`RayDAPOTrainer`：按 UID 聚合 metric、保留组内标准差大于 0 的 group，并补采样到目标 training
batch 或达到生成批次数上限。该 recipe 当前跟随其他 veRL commit，不与本项目 pin 的 0.8.0
直接兼容，不能复制依赖、升级 veRL 或整包移植。M5 只借鉴其算法语义和测试口径。

## 1. E6 — no-mask 对照

### 研究问题与唯一变量

E6 回答：如果把 environment/tool return token 错当作 policy 生成 token 参与 loss，训练和模型行为
会出现什么变化？

**相对 E3 唯一被改变的变量：`response_mask` 中 tool/environment return token 从 0 改为 1。**
模型生成 token 仍为 1，prompt 与 padding 仍不参与 response loss。数据、SFT 起点、rollout、reward、
verifier、工具、parser、optimizer、KL、clipping、seed、监控和评测协议全部与 E3 相同。

不预设 E6 必然崩溃。若性能没有明显下降，仍按真实结果报告，并讨论 50–80 step 的观测窗口和统计
能力限制。

### 最小侵入实现

计划新增独立入口，绝不改变 E3 config 或 veRL site-packages：

- `rl/custom/no_mask_tool_agent_loop.py`：定义 `ToolCreditNoMaskAgentLoop`，复用/继承现有
  `ToolCreditAgentLoop.run()`；拿到 `AgentLoopOutput` 后，仅将实际 `response_ids` 对应的
  `response_mask` 置 1。padding 仍由 veRL postprocess 与 attention mask 相乘后保持 0。
- 在 extra fields 中记录原始 policy-token 数、原始 tool-return-token 数和 no-mask 后 loss-token 数，
  用于证明操纵确实发生；这些字段只用于审计，不进入 reward。
- 新增 E6 专用 agent-loop registration YAML 和 `rl/configs/e6_nomask.yaml`，只把
  `default_agent_loop`/`agent_loop_config_path` 指向 no-mask adapter，并设置独立 project/run 名。
- launcher 尽量复用 E3 的路径解析、preflight、resume、run manifest 和五件套逻辑；若抽取公共 helper，
  必须先用 resolved-config diff 证明 E3 行为未变。
- 将差异与原因追加到 `rl/custom/CHANGES.md`。不 fork veRL，不改安装目录源码。

### 单元测试与静态门禁

在任何 smoke 前扩展 `rl/custom/test_masking.py`，复用同一条包含两个工具返回的确定性轨迹，断言：

1. E3 `ToolCreditAgentLoop` 的 response IDs 与当前 golden 行为一致，assistant/model token mask 为 1，
   tool-return token mask 为 0，padding 为 0。
2. E6 与 E3 的 `response_ids`、tool metadata、终止状态完全一致；仅 tool-return token mask 从 0 变 1。
3. E6 的所有非 padding response token 均进入 loss，prompt 仍在 response tensor 之外，padding 经
   postprocess 后仍为 0。
4. 测试能识别至少一个真实 tool-return token；若轨迹未产生 tool segment，显式失败，避免空断言。
5. E3 回归测试与 E6 差异测试同时通过；不能通过修改原 E3 断言来“适配”E6。

配置门禁检查 E6 与 E3 的 resolved-config diff。允许差异仅为：实验名/输出路径、no-mask agent loop
注册和为 50–80 step 对照设置的训练上限；其余差异视为错误并停止。

### smoke → 正式 run

1. **5-step smoke**：从统一 SFT 起点运行，使用正式数据/rollout 参数，仅缩短总步数与保存路径。
   检查 mask 审计计数非零、loss 可计算、工具链正常、原始轨迹和所有错误指标落盘、checkpoint 可读。
2. smoke 通过并经人工检查至少 8 条含工具返回轨迹后，启动唯一正式 run，建议命名
   `e6_nomask_<UTC timestamp>`，`total_training_steps=80`。
3. 主要严格配对点为 step 0/25/50/75；step 80 作为 E6 运行终点补充报告，不拿它与 E3 的非同一步
   validation 做伪精确比较。正式 run 最少观察到 step 50，除非触发硬故障。
4. 使用 tmux 后台运行，沿用 M4 watcher、25-step checkpoint/eval 和 JupyterHub restart recovery。
   失败或早停也保留 run state、完整日志和最后一个完整 checkpoint。

### 预注册 stop condition

E6 是诊断性反例，不为形式跑满。以下任一情况允许在**完成 step 50 或 step 75 的 checkpoint/eval 后**
早停，并记录触发证据；OOM、NaN、checkpoint 损坏、工具/解析基础设施系统性故障则立即停：

- 连续两个固定 validation 点比 E3 同 step pass@1 低至少 10 个百分点，并且同时出现至少一个行为
  信号（invalid/error 上升、明显输出复读/伪造、response length/truncation 恶化）。
- 连续 5 个 training step 出现明显病理信号之一：`|KL| > 0.01`、entropy `< 0.10`、平均 response
  length `> 2500` token 或 truncation rate `> 20%`；执行时先确认当前 logger 的 KL 符号/口径后再判定。
- step 50 后人工审计样本中，至少 10% 明确模仿/伪造/replay environment output，且固定 panel
  pass@1 同步下降至少 5 个百分点。

单一 noisy step 不触发软早停。若没有达到阈值，跑至 80 并如实记录“未观察到清晰崩溃”。早停不是
成功指标；它只减少已得到清晰结论后的无意义算力。

### 指标与证据

必须保存并按 E3 同 step 比较：

- training total reward、基础 accuracy/format、policy loss；
- 固定 MATH500-100 greedy pass@1；
- entropy、KL、response length、truncated rate；
- tool calls、tool execution error rate、Hermes parser error、invalid rate；
- 每步原始生成轨迹和 mask 审计计数，包括 tool-return token 占 loss token 的比例；
- 模仿/伪造/复读 environment/tool output 的自动候选和人工标签。

自动候选至少覆盖伪造 `<tool_response>`/等价 wrapper、无真实调用却出现环境式输出、长非自然数值或
报错串复读、同一 tool output 多次重复。人工标签使用固定枚举：`imitate`、`forge`、`repeat`、
`legitimate_quote`、`none`；保留原始完整轨迹、sample ID、step、判定理由，不只保存摘要。

### E6 验收

- E3/E6 masking 单测同时证明“E3 正确 mask、E6 仅放开 tool-return token”。
- smoke 接线和审计字段通过，正式 run 完成 80 step 或按预注册条件有证据早停。
- 至少形成一组 E3/E6 同 step 曲线与固定 panel 对照，以及带原始轨迹的 failure-case 集合。
- 结论描述观察到的程度和不确定性，不以“必须崩”为验收条件。
- run 五件套及早停/失败状态完整，可直接供 M7 badcase taxonomy 使用。

## 2. E4 — reward shaping

### 共同定义

两条 E4 run 使用同一个 execution signal：

\[
r_{exec} =
\begin{cases}
n_{success}/n_{calls}, & n_{calls} > 0,\\
0, & n_{calls}=0.
\end{cases}
\]

答案验证继续使用 E3 的 strict `\boxed{}` verifier。工具预算耗尽且没有最终 boxed answer 的 truncated
trajectory 按现行协议总 reward 为 0，shaping 不“救活”该轨迹；工具执行/解析错误继续显式记录。

E4-A 和 E4-B 都从 `sft/checkpoints/qwen3-1.7b-sft` 独立启动并训练 200 step，不从 E3、彼此或其他
RL checkpoint 续训。两条 run 的 treatment 在开跑前同时冻结；不得看过 E4-A 结果后再调 E4-B 系数。

### E4-A — exec-only shaping

参数：

```text
lambda_exec = 0.2
lambda_budget = 0
```

reward：

\[
r_{E4-A} = 1.0\,r_{answer} + 0.1\,r_{format} + 0.2\,r_{exec}.
\]

研究问题：单独给成功工具执行加入 dense process reward，是否能够改善早期学习、工具行为或最终性能？
同时是否诱导 over-calling、重复调用、无意义调用、未使用工具结果或其他 reward hacking？

**E3 → E4-A 唯一被改变的变量是 `lambda_exec: 0 → 0.2`。** `lambda_budget` 保持 0；数据、seed、
rollout、optimizer、KL、clipping、mask、verifier、sandbox 和 fixed validation 全部冻结。

### E4-B — joint shaping

参数：

```text
lambda_exec = 0.2
lambda_budget = 0.1
budget = 3
```

reward：

\[
r_{E4-B} = 1.0\,r_{answer} + 0.1\,r_{format} + 0.2\,r_{exec}
           - 0.1\,\max(0,n_{calls}-3).
\]

研究问题：在 exec-only 的基础上，budget penalty 是否能够抑制 execution bonus 可能导致的过度工具调用
或 reward hacking，同时保留 execution shaping 的潜在收益？

**E4-A → E4-B 唯一被改变的变量是启用 budget penalty：`lambda_budget: 0 → 0.1`，阈值
`budget=3`。** execution bonus 保持 0.2，其余因素全部冻结。E3 → E4-B 是预注册的完整 recipe 总体
效果比较，包含 execution bonus 与 budget penalty 两个共同 treatment，不将该对比误写为单因素因果结论。

### 预注册实验矩阵与比较

E4 只包含下列两条**必做**正式 run，不增加 budget-only 或其他 shaping ablation：

| Run | `lambda_exec` | `lambda_budget` | `budget` | step | 主要作用 |
|---|---:|---:|---:|---:|---|
| E4-A exec-only | 0.2 | 0 | 3（不生效） | 200 | 隔离 execution bonus |
| E4-B joint shaping | 0.2 | 0.1 | 3 | 200 | 在相同 exec bonus 上测 budget penalty |

预注册三个比较，均必须进入结果表和分析：

1. **E3 vs E4-A exec-only**：隔离 execution bonus 对早期学习、最终准确率、工具行为和 hacking 的作用。
2. **E4-A exec-only vs E4-B joint shaping**：判断 budget penalty 是否修正 exec reward 引入的 over-calling、
   重复/无意义调用等副作用，同时保留潜在收益。
3. **E3 vs E4-B joint shaping**：评价完整 shaping recipe 的总体效果。

### 最小实现

- 新增 `rl/configs/e4a_exec_only.yaml` 与 `rl/configs/e4b_joint_shaping.yaml`，均从 E3 配置做显式最小
  差异，并在 resolved config 中落盘各自 reward 参数。
- 在 `rl/custom/reward.py` 让同一 `compute_score` 通过 veRL 0.8.0 已有
  `reward.custom_reward_function.reward_kwargs` 接收 `lambda_exec`、`lambda_budget`、`budget`，再构造
  `RewardConfig`。E3 不传 kwargs 时仍使用全零 shaping 缺省值；如拆 helper，必须用 golden 测试证明
  E3 返回完全不变。不得为 A/B 复制两套 verifier/reward 主逻辑。
- 继续调用 `rewards/composite_reward.py:compute_reward`，不复制 verifier、format reward 或 sandbox。
- 两条 E4 reward 都返回并落盘可审计 breakdown：`base_score`、`exec_success_fraction`、`exec_bonus`、
  `budget_penalty`、最终 `score`、`n_tool_success`。各分量求和必须等于最终 score；truncated 特例显式
  标记。
- E4 共用 launcher/shell infrastructure，但必须显式选择 A/B config 并使用不同 run name/output 目录；复用
  E3 的 preflight、manifest、resume、路径和五件套机制；
  `rl/custom/CHANGES.md` 追加差异说明。

### 测试与配置门禁

在 smoke 前补齐：

1. E4-A/E4-B 分别覆盖 `n_calls=0`、全成功、部分成功、全失败、恰好 3 次、超过 3 次和 truncated 的
   公式边界测试。
2. E3 `compute_score` golden 回归，确保新增 helper 后每个已有字段和值不变。
3. A/B 每个 breakdown 分量、求和一致性、无效/负计数显式报错测试；相同输入下 B 与 A 的差必须严格
   等于 budget penalty。
4. verifier/format 判定与 E3 相同的配对测试；不得为了 shaping 放宽答案正确性。
5. resolved-config 三方 diff：E3 vs A 只允许 exec reward 参数和 run metadata；A vs B 只允许 budget
   reward 参数和 run metadata；两条正式步数均为 200，其他差异一律阻断。

### smoke → 正式 run

1. 先做 **E4-A 5-step smoke**，再做 **E4-B 5-step smoke**：分别确认 reward kwargs/resolved config、
   breakdown、tool success/error counts、validation 和 checkpoint 正常。smoke 之间除 budget 参数外不得有
   接线差异。
2. 每个 smoke 人工抽查至少 8 条，手算 reward 并与 JSONL 对齐；任何 verifier/reward/parser 静默错误都
   阻断对应正式 run。
3. 按顺序启动两个独立 200-step 正式 run，建议命名
   `e4a_exec_only_<UTC timestamp>`、`e4b_joint_shaping_<UTC timestamp>`；tmux、watcher、25-step
   save/eval 和 restart recovery 与 E3 相同。
4. A/B reward 设计在两条正式 run 前冻结。发现 hacking 时保留证据，不得中途修改参数或根据 A 的结果
   调整 B 后继续声称是预注册比较。

### 比较方法

- 三个预注册 pairwise comparison 都使用相同绘图、指标窗口和统计口径，不只报告其中有利的一组。
- **early convergence**：比较 step 0–100 的 validation pass@1 AUC，以及首次达到 0.67、0.70、0.73
  的 step；未达到按 right-censored 报告。training reward 同时拆为 base 与 shaping，避免把 bonus 当准确率。
- **final performance**：固定 MATH500-100 step-200 greedy pass@1、峰值及其 step；以 final 为主，peak
  为辅。
- **tool behavior**：每轨迹 calls 分布、0/1/2/3/4-call fraction、成功率、重复调用率、是否实际使用
  tool result、trivial/no-op 调用、response length/truncation。A vs B 特别比较第 4 次调用及 budget 边界行为。
- **错误**：invalid、parser error、tool execution error 与 format failure，按相同口径和 cadence 比较。
- 每条 run 都同时画 `base_score/acc`、fixed-panel pass@1 与 shaped `score`，显式检查是否出现 reward 上升
  但真实 accuracy 不升；绝不把 shaped reward 上升直接解释为任务准确率上升。

### reward hacking 检测与 M7 证据

E4-A 与 E4-B 分开生成 candidate manifest，并使用同一规则自动筛选、保留以下完整原始轨迹：

- `acc=0` 但拿到完整或接近完整 exec bonus；
- 多次运行相同/归一化后相同的简单代码，尤其是结果未被后续 reasoning/final answer 使用；
- no-op、常量打印、无关算术等只为获得 success 的调用；
- over-calling、第四次调用前后的行为突变，或 E4-B 为规避 penalty 提前给出低质量答案；
- shaped reward 上升而 base accuracy、固定 panel pass@1 不升；
- tool-call 数/成功率显著上升，但 answer accuracy、invalid/error 没有相应改善。

每个正式 eval 点、每条 run 生成候选清单；每条 run 结束后分别人工审计不少于 20 条候选（若候选不足
则审计全部），记录 `sample_id`、step、完整 prompt/assistant/tool 轨迹、reward breakdown、代码归一化
hash、标签和理由。另生成 E3/E4-A/E4-B 的 aggregate hacking-rate/tool-behavior 对比，重点回答 B 是否
减少 A 中出现的副作用以及是否牺牲 accuracy。重点案例复制索引而不改写原始证据，预留给 M7
`04_reward_hacking.md`。建议标签为
`redundant_repeat`、`trivial_exec`、`unused_result`、`penalty_avoidance`、`legitimate_use`、`uncertain`。

### E4 验收

- E4-A/E4-B 公式、边界、E3 回归、A/B 差分和 breakdown tests 通过。
- **E4-A exec-only 与 E4-B joint shaping 两条必做 run 均独立完成 200 step**，各自五件套完整；不以一条
  替代另一条，不增加 budget-only 或其他 shaping ablation。
- E3 vs A、A vs B、E3 vs B 三个预注册比较均报告 early AUC/threshold、final pass@1、tool-call
  distribution、execution success/error、repeated/trivial/unused calls、invalid/parser error/truncation。
- 两条 run 分开报告 shaped reward 与真实 answer accuracy/fixed-panel pass@1，并明确是否出现 reward
  上升但 accuracy 不升。
- A/B 各自的 hacking candidate 和人工审计记录可复核；A vs B 的对比证据能进入 M7
  `04_reward_hacking.md`。
- 不改变 verifier 口径；不把 E3 vs E4-B 解释为单独 budget penalty 的因果效应。

## 3. E7 — DAPO-style dynamic filtering / sampling（本次必做）

### 研究问题与唯一变量

GRPO 将同一 prompt 的 8 条 rollout 组成一组。若该组用于 advantage 的标量 reward 完全相同，
group-relative advantage 为零，这组 rollout 消耗生成算力却不提供有效 policy-gradient 信号。E7 回答：
动态过滤零方差 group 并补采样，是否提高每个有效 update 和每单位 rollout compute 的学习效率？

**相对 E3 唯一被改变的实验因素是 training group 的选择/补采样策略**：在 actor update 前丢弃
`std(score)=0` 的 group，并用同一 actor snapshot 动态生成新的 prompt groups，直到凑齐 64 个有效
group 或达到安全上限。reward 仍是 E3 的 unshaped `score`，mask 仍是 E3 正确 mask；其余配置保持一致。

E7 从同一 SFT checkpoint 平行训练 200 个**有效 actor update**，不从 E3 或 E4 续训。

### 为什么使用 `score`，而不是只看 `acc`

E3 的 advantage 基于实际标量 `score = answer + 0.1 * format`，因此“无效组”必须定义为同一 UID 的
8 个 `score` 完全无方差（实现时用数值容差/`max-min` 与 std 双重检查），而不是简单的全对/全错。

对 E3 原始训练 JSONL 的离线只读审计显示：

- 平均 `acc` 全对组约 33.74%，全错组约 17.70%，mixed 约 48.55%；
- 按实际 `score`，零方差组约 44.07%，informative 约 55.93%，理论 prompt 倍率约 `1/0.5593=1.79`；
- 最后 25 step informative 约 47.25%，历史最低单步约 39.06%；
- 平均约 7.38% 的 group 虽然 `acc` 一致，但 `score` 因 format 项而有方差。

因此用 `acc` 过滤会误删仍有 format-gradient 的 group。上述数字只用于预算，不预设 E7 实际分布。
同时继续记录 all-correct/all-wrong/mixed，方便解释数据难度变化。

### 实现决策：现成配置不足，需仓库内最小 trainer adapter

不能把 `algorithm.filter_groups.enable=true` 当作完成。忠实的 on-policy 动态补采样发生在
`RayPPOTrainer.fit()` 的“取 prompt → rollout → reward → 按 UID 过滤 → 补采样 → advantage → actor
update”数据流中；agent loop、reward function 或普通 callback 都拿不到完整跨 group batch，也无法在同一
actor update 前驱动额外 rollout。

计划采用：

- `rl/custom/dynamic_filter_trainer.py`：定义 repo-local `DynamicFilterRayPPOTrainer`，继承 pin 版本
  `RayPPOTrainer`，只改写上述数据流所必需的最小片段；不 fork、不修改 veRL 安装目录。抽出小函数完成
  UID 聚合、metric 校验、筛选、拼接、截取和 ledger 生成。
- `rl/launch/e7_dynamic_filtering.py`：repo-local TaskRunner 显式构造该 trainer，复用 E3 launcher 的
  配置解析和 run infrastructure。不能依赖 v0.8.0 `main_ppo.py` 自动选择 trainer，因为其 TaskRunner
  硬编码标准 `RayPPOTrainer`。
- `rl/configs/e7_dynamic_filtering.yaml`：继承 E3 值并显式设置
  `algorithm.filter_groups.enable=true`、`metric=score`、`max_num_gen_batches=4`。这三个官方字段在 E7
  中由 repo-local adapter 消费；resolved config 和启动日志必须打印“实际 trainer 类 + 实际过滤参数”。
- 每个 generation chunk 仍为 64 个 prompt、每 prompt 8 trajectories；每次有效 update 选择采样顺序中
  前 64 个 informative groups。多出的 informative group 不回收到下一 actor snapshot，作为 unused surplus
  保存，避免跨 policy 混用；零方差组保存但不训练。
- 最大 **4 个 generation batches/有效 update（首次 1 批 + 最多补 3 批）**。达到上限仍不足 64 个
  informative groups 时显式失败并保存当步全部候选，不做 underfilled update、不无限补采样。
- 同一有效 update 的全部候选必须由同一冻结 actor snapshot 生成；补采样结束后才计算 advantage/更新
  actor。rollout replicas 的 sleep/wake 时序需在 adapter 中显式处理和测试。
- checkpoint 只在完整有效 update 后保存；恢复状态必须包含 global effective step、train sampler/dataloader
  状态和累计采样 ledger，防止 JupyterHub restart 后重复/跳过数据而不可追溯。
- 追加 `rl/custom/CHANGES.md`，精确记录覆盖的 veRL 方法/代码段、pin 版本、行为差异和回退路径。

这是对框架内部 trainer/data-flow 的行为改写。**用户批准整份 M5 计划后，在真正实现 E7 trainer
data-flow override 前，仍必须单独展示 exact implementation/diff boundary（将覆盖的类、方法、代码段、
新增文件和不触及的边界）并再次获得用户批准。** 若届时 pin 源码或扩展点有变化，重新核对，不凭本计划
直接写代码。

### 不改内部 trainer 的替代方案及其局限

- 仅写 YAML：v0.8.0 trainer 不消费字段，无法实现。
- 预先离线筛 prompt 或做 static curriculum：不能根据当前 actor 的 8 条 rollout reward 方差动态决定，
  不回答研究问题。
- 生成后只把零方差 group 的 loss mask 清零：能避免无效 loss，但不补回有效 batch，不能衡量 DAPO-style
  样本效率，且仍浪费同样 rollout。
- 升级 veRL/直接移植 `verl-recipe`：会同时改变大量框架行为和依赖，破坏 E3 可比性并违反 pin/最小侵入。

因此没有“不触及 trainer 内部数据流但仍忠实实现 E7”的等价方案。若用户不批准该 adapter，E7 应标记
blocked 并回报，不能用上述近似替代后声称完成。

### 测试门禁

在任何 GPU smoke 前运行纯 CPU/小张量确定性测试：

1. 同一 UID 恰有 8 条；缺失、重复、非数值/NaN metric 或 group size 不符立即报错。
2. `score` 全同的全对、全错、仅 format 一致组被过滤；`acc` 一致但 `score` 有差异的组被保留。
3. 多批候选按确定顺序累积，恰取 64 个 informative groups；零方差和 surplus 都有明确 reason。
4. 达到 4 批仍不足时显式失败，不进行 actor update。
5. 筛选后每组仍有 8 条、UID/response/reward/mask/non-tensor metadata 对齐，advantage 只对选择数据计算。
6. `enable=false` 的 adapter 路径与标准 E3 选择结果一致；同时做一项负测试证明“只设官方字段而使用
   标准 RayPPOTrainer 不会被误认作已启用”。
7. ledger 计数守恒：sampled = filtered zero-std + selected + unused surplus，prompts 与 trajectories 的
   8 倍关系正确，累计值在模拟 resume 后连续。
8. resolved-config diff 仅允许过滤配置、trainer/launcher 类、实验/输出名称；reward/mask 与 E3 一致。

### smoke → 正式 run

1. 在专项实现批准后完成静态/CPU 测试，再进行 **5 个有效 update 的 smoke**。检查至少发生一次实际
   补采样；若自然没有零方差组，用测试 fixture 验证机制，不能修改正式 reward 诱发过滤。
2. smoke 必须证明：actor 每个 effective step 只更新一次；所有候选来自更新前同一 actor；64 个有效
   group；无 UID/metadata 错位；ledger、raw candidates、checkpoint 和 resume 可读。
3. 正式 run 建议命名 `e7_dynamic_filtering_<UTC timestamp>`，完成 200 个有效 actor update；
   save/eval cadence 按 effective step 的 0/25/.../200，与 E3 曲线可对齐。
4. 训练池、seed 和初始 sampler order 与 E3 相同，但由于 E7 会额外消费 prompt，其后采样序列不可避免地
   与 E3 分叉。这是实验变量的直接后果，必须在 manifest 和偏差记录中声明，不重新调 seed 来追求表面对齐。
5. tmux/watch/restart 规则沿用 M4；达到补采样上限、ledger 不守恒、resume 不一致或 reward/mask 漂移时
   立即停止，不以 underfilled batch 降级继续。

### 每个有效 update 的采样 ledger

除 E3 通用指标外，逐 update 持久化：

- `sampled_prompts`、`sampled_trajectories`、`selected_prompts=64`；
- `zero_std_groups`、`group_all_correct_frac`、`group_all_wrong_frac`、mixed/informative group fraction；
- `num_gen_batches`、`unused_informative_surplus`、按 filter reason 的数量；
- response/rollout token 数、生成 wall-clock、补采样 wall-clock、完整 effective update wall-clock；
- cumulative sampled prompts/trajectories/tokens/GPU time；
- 每条 candidate 的 UID/sample ID、8 条 scalar score、acc/format、selected 标记和 filter reason。

原始候选轨迹无论 selected、zero-std 还是 surplus 都要保留；训练 JSONL 与分析 JSONL 区分，不能让
“未用于更新”样本从证据中消失。

### 比较与结论口径

E7 至少提供四个横轴：

1. reward / fixed-panel pass@1 vs **effective actor update**；
2. reward / pass@1 vs **累计 sampled trajectories**；
3. reward / pass@1 vs **累计 rollout tokens 或 rollout wall-clock**；
4. 每次 effective update 的 wall-clock 与 E3 普通 step wall-clock。

核心效率量包括：过滤前零方差比例、每 64 个有效 prompts 实际采样多少 prompts/trajectories、rollout
倍率、补采样上限命中率、每有效 update 时间。最终不仅回答 pass@1 是否上升，还要回答：

> dynamic filtering 是否减少了进入 actor update 的无梯度 group；为了补齐有效 batch 付出的额外 rollout
> 是否使 pass@1-per-trajectory/token/time 真正改善？

可能出现“每 update 学得更快，但每 rollout 更差/无改善”；这同样是有效结论，不以最终准确率上涨为验收
条件。

### E7 验收

- 源码证据明确说明 v0.8.0 标准 trainer 不消费 filtering config，没有宣称 YAML-only 可用。
- 用户对 trainer adapter 给予专项批准后才实施；实现保持 repo-local、pin 不变、无 veRL fork/site-packages
  改动。
- CPU tests、5-update smoke 和 200-effective-update 正式 run 依次通过，或出现显式、可诊断的硬停止。
- 每步 ledger 守恒，过滤定义与实际 GRPO scalar `score` 一致，raw candidates 可复核。
- 同时报告 per-update 与 per-rollout/token/time 效率，能回答额外采样成本是否值得。
- 采样效率统计可直接进入 M7 主表/附录。

## 执行顺序与算力预算

建议顺序为 **E6 → E4-A exec-only → E4-B joint shaping → E7**：

1. **公共静态接线与 E6（约 0.5 日 + 3–4 GPU 小时）**：E6 成本最低，可先证明 M5 的 config diff、
   mask 证据、monitor、run 五件套和早停机制可靠。
2. **E4-A（共享 reward 接线约 0.5 日 + 9–10 GPU 小时）**：先测 exec-only，形成 execution bonus 的
   独立对照和 hacking evidence。
3. **E4-B（约 9–10 GPU 小时）**：参数预先冻结，在完全相同 setup 中仅加入 budget penalty，直接与
   E4-A 比较其修正作用。
4. **E7（约 1–1.5 日实现/测试 + 12–14 GPU 小时估算）**：依赖单独的内部 data-flow 批准，且补采样、
   resume 和效率 ledger 风险最高，放在前三条已验证 infrastructure 之后。
5. **统一分析与 M5 验收（约 0.5–1 日）**：同一绘图/评测入口整理 E3/E4-A/E4-B/E6/E7，不执行
   M6 或 M7 全量工作。

总估算约 **6 个日历日、33–38 GPU 小时**。其中 E6 约 3–4 小时、E4-A 约 9–10 小时、E4-B
约 9–10 小时、E7 约 12–14 小时；smoke 和失败重启不作为可随意扩张的隐藏预算。E7 按 E3 informative
比例预估约 1.8× prompt rollout，实际由 ledger 报告，预算不是结果。磁盘按四个独立 M5 run、raw
candidates 和 checkpoint 预留至少 200 GiB，启动前以真实余量复核。

E4-A、E4-B 和 E7 均为必做。时间不足时优先取消额外 seed、额外 shaping ablation 或非必要绘图，不能
取消任一必做 run，也不能把 E7 静默降回 optional。

## 风险与降级方案

| 风险 | 预防/检测 | 降级或停止方式 |
